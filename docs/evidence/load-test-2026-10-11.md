# Load / performance -- measured

Run 2026-10-11T16:54:02.525Z against `http://127.0.0.1:3200`.
Production image, concurrency 20, 10s per scenario after a 3s warmup.

## Results

| Scenario | req/s | p50 | p90 | p95 | p99 | max | errors |
|---|---:|---:|---:|---:|---:|---:|---:|
| health (no auth, no db) | 6034 | 2.3 ms | 5.3 ms | 8.8 ms | 14.4 ms | 37.6 ms | 0 |
| list contacts (first page) | 418 | 33.4 ms | 105.5 ms | 133.8 ms | 216.6 ms | 485.4 ms | 0 |
| list contacts (deep page) | 428 | 31.8 ms | 106.1 ms | 137.6 ms | 214.2 ms | 369.2 ms | 0 |
| list deals (first page) | 419 | 32.9 ms | 105.6 ms | 138.5 ms | 217.3 ms | 473.4 ms | 0 |

## What each scenario is

- **health (no auth, no db)** -- Baseline for framework overhead alone. Any latency here is Express, not PostgreSQL.
- **list contacts (first page)** -- The workhorse query: paginated, tenant-scoped, sorted.
- **list contacts (deep page)** -- Offset pagination degrades with depth. This is where a missing index shows up first.
- **list deals (first page)** -- Second tenant-scoped list, to check the behaviour is not specific to one table.
- **current org + membership** -- Auth path: token verification and the tenant lookup that every request performs.

## Reading these numbers

- Slowest tail: **list deals (first page)** at p99 217.3 ms.
- Aggregate error rate across all scenarios: **0.00%**.

Two caveats that bound what these figures mean, stated rather than assumed:

1. **Same-host measurement.** The generator and the target share a machine, so
 these numbers cover the application and the database, not a network. Real
 client latency adds round-trip time and TLS handshakes on top. Treat these
 as a floor, not as what a user will observe.
2. **Read-only.** The harness issues no writes, deliberately: a benchmark that
 creates rows makes its own next run slower and stops being comparable.
 Sustained write throughput is therefore **unmeasured**, and is recorded as
 such rather than estimated.
3. **Rate limits lifted.** The run used `RATE_LIMIT_GLOBAL_MAX=100000`,
 `RATE_LIMIT_SEARCH_MAX=10000`, and 1 s windows, against production defaults
 of 1000/15 min and 60/15 min. The numbers describe the application and
 database, not the abuse controls -- which are covered by the security suite.
 Do not read these as achievable under the default limits.
4. **Pool-sized.** `DB_POOL_MAX=20` with 20 workers. Each authenticated request
 issues at least two queries (session/tenant lookup, then the list), so the
 pool is the likeliest source of the p90-p99 spread: at p50 a connection is
 free, at p99 twenty workers are contending for twenty connections. Raising
 the pool would narrow the tail right up to the point where PostgreSQL itself
 becomes the bottleneck instead.
